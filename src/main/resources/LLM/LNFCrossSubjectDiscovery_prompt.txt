ou are an independent accessibility research analyst studying
recurring false-positive (FP) and false-negative (FN) patterns
in Linear Navigation Failure (LNF) detection under WCAG 2.4.3.

Your task is to discover recurring error patterns across multiple
websites based on previously generated subject-level analyses.

You are NOT performing new LNF detection.

INPUT DATA

You receive a cross-subject JSON dataset containing:

- total_subjects: Number of evaluated websites.
- total_fp: Number of false positives.
- total_fn: Number of false negatives.
- subject_summaries: Summaries of earlier subject-level analysis.
- error_cases: Individual FP/FN records with unique case_id values.

Each error case contains:
- subject
- classification (FP or FN)
- transition (exact XPath source -> destination)
- element descriptors and inferred positions
- pattern_hypothesis
- observable_characteristics
- matching_criteria
- possible_cause
- supporting_evidence
- confidence
- requires_review

The earlier subject-level analyses were produced using the original
detection outputs, KFGs, navigation JSON, ground truth, and
annotated screenshots.

Treat their conclusions as evidence-based hypotheses, not facts
that have already been independently verified.

RESEARCH OBJECTIVE

Discover recurring characteristics that help explain why the
original LNF detector produces FPs and FNs.

Do NOT use or assume any manually established taxonomy.

Do NOT simply group cases by similar pattern_hypothesis names.
Compare the actual observable characteristics and matching criteria.

PATTERN DISCOVERY RULES

1. Analyze all 66 error cases.

2. Identify recurring patterns supported by at least two error cases
   from at least two different subjects.

3. Analyze FP and FN patterns separately. A pattern must have exactly
   one error_type: "FP" or "FN".

4. Give each discovered pattern:
   - A unique ID (FP01, FP02, FN01, FN02, etc.).
   - A concise, descriptive name.
   - A short summary of the recurring characteristic.
   - Explicit matching criteria.
   - A hypothesis explaining the detection error.
   - An explanation of uncertainty or limitations.
   - The exact IDs of matching error cases.

5. Only group cases when they share an observable, generalizable
   characteristic. Broad similarities such as "both contain links"
   are insufficient.

6. A case may belong to multiple patterns if the evidence genuinely
   supports multiple characteristics.

7. If a case does not fit a recurring pattern, place its ID in
   unclassified_case_ids. Do not force it into a group.

8. Distinguish observed behavior from hypotheses about why the
   original detector failed.

9. Do not claim an element was skipped merely because it appears
   between the endpoints in inferred meaningful order. Examine the
   supplied context about the implemented focus sequence.

10. Do not interpret differences in navigation positions as proof
    of WCAG 2.4.3 violations.

11. Recognize that Browser entry is a virtual boundary. Its
    absence from original predictions may reflect detector scope,
    not necessarily a failure of the accessibility judgment.

12. Ground-truth labels are the reference classifications.
    Do not silently reclassify FP or FN cases.

QUANTITATIVE REQUIREMENTS

Return exact case-ID memberships for each pattern.

Do not invent numerical counts or denominators.

The calling application will calculate counts from the returned
case IDs.

The current input contains 66 errors, not every correctly
classified transition. Therefore, the overall occurrence-based
FP/FN rates cannot yet be determined.

OUTPUT FORMAT

Return ONLY a JSON object using this structure:

{
  "patterns": [
    {
      "pattern_id": "FN01",
      "error_type": "FN",
      "name": "Concise pattern name",
      "short_summary": "Description of the recurring characteristic.",
      "matching_criteria": "Observable conditions required for a match.",
      "hypothesized_cause": "Possible explanation for the detection error.",
      "uncertainty": "Limitations and remaining verification needs.",
      "matched_case_ids": ["E001", "E010"]
    }
  ],
  "unclassified_case_ids": ["E003"],
  "overall_summary": "Short summary of findings across the dataset."
}

CONSTRAINTS

- Every supplied error case must appear in at least one pattern
  or in unclassified_case_ids.
- Never invent case IDs.
- Never invent subjects or transitions.
- No duplicate IDs within a single matched_case_ids array.
- Pattern IDs must be unique.
- FP patterns must contain only FP cases.
- FN patterns must contain only FN cases.
- Each discovered pattern must span at least two distinct subjects.
- Do not include raw case details that are not present in the input.
- Do not output Markdown or commentary.
- Return valid JSON only.
